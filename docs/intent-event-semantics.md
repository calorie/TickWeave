# Intent and Event Semantics Specification

Status: **Authoritative v0.1**

This specification defines the semantic transaction model used by TickWeave.

## 1. Roles

- **MutationIntent** requests one semantic transaction.
- **AtomicIntent** requests multiple semantic operations as one all-or-nothing transaction.
- **SimulationEvent** makes future causal work eligible at a logical ResolutionPoint.
- **ResourceKey** defines authoritative conflict granularity.

Events are not mutations. Events are evaluated into Intents.

## 2. Stable IDs

Representative semantic IDs:

```rust
type TickId = u64;
type WaveId = u32;
type Revision = u64;

struct WorldId([u8; 16]);
struct ObjectId([u8; 32]);
struct IntentId([u8; 32]);
struct AtomicIntentId([u8; 32]);
struct EventId([u8; 32]);
struct InputId([u8; 32]);
struct ScheduleId([u8; 32]);

struct ResolutionPoint {
    tick: TickId,
    wave: WaveId,
}
```

IDs generated by the simulation are derived deterministically with domain-separated cryptographic hashing (BLAKE3-256 is the intended primitive).

Example:

```text
IntentId = H("intent/v1", cause_id, emission_index)
EntityId = H("entity/v1", creating_intent_id, spawn_index)
EventId  = H("event/v1", cause_id, emission_index)
```

Random UUID generation is forbidden for deterministic semantic identities.

## 3. Canonical ResourceKey

Authoritative mutable state is addressed through canonical ResourceKeys.

Representative model:

```rust
enum ResourceKey {
    Block { dimension: DimensionId, pos: BlockPos },

    BlockEntityExistence {
        dimension: DimensionId,
        pos: BlockPos,
    },
    BlockEntityComponent {
        dimension: DimensionId,
        pos: BlockPos,
        component: ComponentTypeId,
    },

    EntityExistence { entity: ObjectId },
    EntityComponent {
        entity: ObjectId,
        component: ComponentTypeId,
    },

    ContainerSlot {
        container: ObjectId,
        slot: u32,
    },
    ContainerComponent {
        container: ObjectId,
        component: ComponentTypeId,
    },

    ScheduledObject { schedule_id: ScheduleId },

    WorldState {
        namespace: NamespaceId,
        key: CanonicalKey,
    },

    PluginState {
        plugin: PluginId,
        key: CanonicalKey,
    },
}
```

ResourceKey has a platform-independent canonical binary encoding and total byte ordering.

Derived caches/indexes are not authoritative resources. Spatial indexes, lookup caches, routing caches, halo caches, and packet state must be reconstructible.

### Existence conflicts

Every EntityComponent access implicitly reads `EntityExistence(entity)`.

Entity deletion writes the corresponding existence key, therefore deletion conflicts with all component mutation.

Equivalent rules apply to BlockEntity lifecycle.

## 4. Canonical numeric/state representation

Authoritative state must not depend on platform-specific unordered iteration or floating behavior.

Semantic iteration uses canonical ordering.

NaN-bearing values are not accepted as authoritative numeric state.

The initial design direction is integer/fixed-point authoritative physics representation (for example Q32.32 where suitable), with Minecraft protocol floating conversion at the Gateway edge.

Exact per-domain numeric types may be refined without weakening deterministic equality.

## 5. Versioned Operation

An Intent never contains an arbitrary closure.

```rust
struct OperationSchemaId {
    namespace: u32,
    operation: u32,
    version: u32,
}

struct Operation {
    schema: OperationSchemaId,
    payload: CanonicalBytes,
}
```

Every schema deterministically provides:

```rust
trait OperationSchema {
    fn validate_payload(payload: &CanonicalBytes) -> Result<(), SchemaError>;
    fn access_plan(payload: &CanonicalBytes) -> AccessPlan;
    fn resolve(ctx: &mut TransactionContext, payload: &CanonicalBytes)
        -> OperationResult;
}
```

`access_plan` must be complete before resolution starts.

`resolve` may not expand its ResourceKey access set.

## 6. Access plan

```rust
struct AccessPlan {
    transactional_reads: Vec<ResourceKey>,
    writes: Vec<WriteAccess>,
}

struct WriteAccess {
    key: ResourceKey,
    mode: WriteMode,
}

enum WriteMode {
    CompareAndSet { expected_revision: Revision },
    Sequential,
}
```

Vectors use canonical sort order and contain no duplicates.

An EVALUATE-time snapshot observation is not itself a transactional read. If correctness requires the observed value to remain valid, the resulting operation must encode an appropriate guard/CAS/read dependency.

## 7. Write modes

### CompareAndSet

CAS is the default for ordinary exclusive world mutation.

A transaction expecting revision R succeeds only if the provisional serial state still has R when the transaction is evaluated.

This produces deterministic **first successful transaction wins**, not last-write-wins.

### Sequential

Sequential is allowed only for operation schemas whose semantics explicitly compose against the latest provisional state.

Example: independent damage operations may all apply in canonical serial order.

### Commutativity

Commutativity is not a semantic WriteMode.

The semantic truth is canonical serial execution. The runtime may combine/reorder physically only when it proves the optimized result is bit-identical to canonical semantics.

## 8. Guards

Standard guards may include:

```rust
enum Guard {
    Exists(ResourceKey),
    NotExists(ResourceKey),
    RevisionEq { key: ResourceKey, expected: Revision },
    ValueHashEq { key: ResourceKey, expected: [u8; 32] },
}
```

Operation-specific conditions are evaluated through declared transactional reads.

A gameplay guard failure is a normal deterministic rejection, not a runtime fault.

## 9. MutationIntent

```rust
struct MutationIntent {
    id: IntentId,
    world: WorldId,
    point: ResolutionPoint,
    cause: CauseRef,
    origin: OriginRef,
    operation: Operation,
}
```

It executes one Operation atomically.

## 10. AtomicIntent

```rust
struct AtomicIntent {
    id: AtomicIntentId,
    world: WorldId,
    point: ResolutionPoint,
    cause: CauseRef,
    origin: OriginRef,
    operations: NonEmptyVec<Operation>,
}
```

Nested AtomicIntent is forbidden.

Members execute in vector order against a private provisional transaction state.

The union of all member access plans is known before execution starts.

Any member failure rejects the whole transaction. No partial state or buffered event becomes visible.

## 11. Cause and origin

Representative cause chain:

```rust
enum CauseRef {
    ExternalInput(InputId),
    SimulationEvent(EventId),
    Scheduled(ScheduleId),
    Intent(IntentId),
    AtomicIntent(AtomicIntentId),
    System(SystemCauseId),
}
```

Origin records stable semantic source information for tracing and source-sequence constraints. It must not contain Worker, Cell, process, or thread identity.

## 12. Transaction context

Resolvers receive only deterministic capabilities:

```rust
trait TransactionContext {
    fn read(&self, key: &ResourceKey) -> StateValue;
    fn revision(&self, key: &ResourceKey) -> Revision;
    fn write(&mut self, key: &ResourceKey, value: StateValue);
    fn delete(&mut self, key: &ResourceKey);
    fn emit(&mut self, event: EventDraft);
    fn deterministic_random(
        &self,
        stream: RandomStreamId,
        invocation: u32,
    ) -> RandomValue;
}
```

Forbidden capabilities include wall clock, system RNG, arbitrary filesystem/network access, thread creation, sleep/blocking I/O, Worker ID, and Cell ID.

Access outside the declared access plan is a `RuntimeDeterminismFault`, not a gameplay rejection.

## 13. Revisions

Each ResourceKey has a logical Revision.

A committed transaction that changes a key increments its revision exactly once, even if an AtomicIntent writes that key multiple times internally.

Rejected transactions do not increment revisions.

## 14. Conflict definition

Two transactions conflict if they share a ResourceKey K and at least one writes K:

```text
write/write  => conflict
write/read   => conflict
read/write   => conflict
read/read    => no conflict
```

AtomicIntent participates using the union of its members' access plans.

## 15. Conflict graph

For each ResolutionPoint:

```text
node = MutationIntent or AtomicIntent
edge(A,B) = conflicts(A,B)
```

Connected components may be resolved independently and physically in parallel.

The world must never be forced through one global transaction queue.

## 16. Canonical serializability

Each connected conflict component must produce exactly the result of one defined canonical serial execution:

```text
DistributedResolution(component)
==
CanonicalSerialExecution(component)
```

Physical execution may be parallel/distributed.

## 17. Happens-before

The canonical order honors explicit causal constraints including:

- earlier sequence in the same normalized input stream;
- cause before work directly emitted from that cause when they share a resolution ordering domain;
- AtomicIntent member order;
- earlier reactive Wave before later reactive Wave.

The precise graph must be acyclic; cycles indicate a specification/runtime fault.

## 18. Deterministic tie-break

Concurrent ready transactions without a happens-before relation use a deterministic tick-local tie-break:

```text
tie_break =
  H(
    "intent-order/v1",
    world_order_seed,
    tick,
    wave,
    intent_id
  )
```

A deterministic topological sort repeatedly chooses the ready node with minimum tie-break value.

IntentId is only the final hash-collision fallback.

This avoids making a low permanent actor/object identifier win every conflict forever.

## 19. Rejection

Normal transaction outcomes:

```rust
enum TransactionStatus {
    Accepted,
    Rejected(RejectReason),
}
```

Representative rejection reasons include guard failure, revision mismatch, resource missing/already present, and semantic rule violation.

Rejected transactions remain part of the canonical ordering but produce no authoritative state delta.

Invalid schema, undeclared access, non-canonical payload, illegal dependency expansion, and forbidden nondeterminism are runtime faults. The affected ResolutionPoint must not silently commit.

## 20. Event buffering

Events emitted by an Intent/AtomicIntent are transaction-local EventDraft values.

Only after the transaction is accepted are stable EventIds materialized and the events admitted for future delivery.

Rejected transactions emit no events.

## 21. SimulationEvent

```rust
struct SimulationEvent {
    id: EventId,
    world: WorldId,
    cause: CauseRef,
    source: EventSource,
    target: EventTarget,
    deliver_at: ResolutionPoint,
    schema: EventSchemaId,
    payload: CanonicalBytes,
}
```

Targets are stable semantic addresses such as EntityId, block position, scheduled object, or logical service object.

EventTarget MUST NOT contain WorkerId, CellId, NodeId, or network address.

Routing is resolved at delivery time against current authority.

## 22. Delivery semantics

Physical event transport may be at-least-once.

Semantic admission is exactly-once by stable EventId.

Duplicate physical delivery is deduplicated.

Network arrival order is never semantic order.

An event emitted in Wave W is eligible no earlier than Wave W+1.

Future-Tick delivery is valid.

## 23. Dependency admission and remote expansion

A ResolutionPoint cannot dynamically acquire an arbitrary previously unrelated remote participant after its dependency set begins closing.

Long-range work is represented by a future SimulationEvent, allowing the target dependency to be admitted before that future point opens.

Local neighbor propagation may traverse Cell boundaries within the same Tick via successive Waves.

## 24. Cross-authority AtomicIntent

AtomicIntent may span multiple authorities.

Its semantics remain all-or-nothing.

A physical implementation may use a deterministic coordinator and distributed prepare/decision protocol, but coordinator placement is not semantic.

Conceptual protocol:

```text
CLOSE participant/intent set
 -> GATHER required provisional state
 -> RESOLVE canonical serial component
 -> PREPARE participant deltas
 -> DURABLE DECISION
 -> COMMIT/idempotently apply
 -> ADVANCE frontier
```

A durable COMMIT decision survives coordinator/participant failure and is replayed idempotently.

There is no legal partial distributed semantic commit.

## 25. Creation and deletion

Creation asserts non-existence of the authoritative existence resource.

Deletion mutates/deletes the existence resource and therefore conflicts with component access.

Physical garbage collection may lag semantic deletion.

## 26. Deterministic random inside operations

Operation random is derived from stable semantic identity, for example:

```text
Random(
  world_seed,
  intent_id,
  operation_member_index,
  stream_id,
  invocation_index
)
```

Topology/runtime identity is forbidden.

## 27. Typed construction boundary

Gameplay modules and plugins should not manually construct arbitrary raw access plans.

They call typed host APIs such as:

```text
request_block_replace(...)
request_damage(...)
request_inventory_transfer(...)
```

The host implementation creates validated, versioned canonical operations.

This prevents modules from manufacturing incorrect conflict declarations.

## 28. Reference resolution algorithm

At each ResolutionPoint:

```text
seal admitted causal work
 -> validate schemas/canonical payloads
 -> derive complete access plans
 -> build conflict graph
 -> split connected components
 -> build happens-before DAG per component
 -> deterministic topological sort
 -> execute against provisional transaction state
 -> buffer accepted events
 -> produce canonical component deltas
 -> establish durable decision
 -> apply/commit idempotently
 -> materialize accepted events
 -> advance frontier
```

## 29. Required properties

The implementation must demonstrate:

- Atomicity
- deterministic canonical serializability
- durability according to policy
- replay idempotence
- causal ordering
- Partition Invariance
- no duplicate semantic event admission
- no committed entity/item duplication or loss due to retry/migration
- equivalent local and remote interaction semantics

## 30. Architectural summary

```text
MutationIntent / AtomicIntent
    define WHAT semantic transaction is requested.

SimulationEvent
    defines WHEN and WHERE future causal work becomes eligible.

ResourceKey
    defines WHAT can conflict.

Canonical serializability
    defines deterministic conflict outcome.

Cell / Worker / transport
    define only WHERE computation happens.
```
